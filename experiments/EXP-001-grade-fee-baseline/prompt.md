## Turn 1 (사용자 → AI, 2026-10-12)

# Phase 2 — 실험 범위 확정 및 최초 비즈니스 코드 구현

너는 Java 21 기반 프로젝트를 진행하는 시니어 개발자다.

## 프로젝트 목적

AI가 작성한 코드에 대해 다음 두 테스트 접근법을 비교한다.

A. Claude가 직접 테스트 필요성을 판단하고 테스트를 작성한다.

B. Jev가 테스트 필요 점수를 산출하고, Claude가 그 결과를 참고하여 테스트를 작성한다.

이후 PIT 뮤테이션 테스트를 통해 두 방식의 결함 탐지 능력을 비교한다.

이 프로젝트는 정산 시스템의 완성이 아니라 테스트 방법론을 경험하기 위한 작은 실험이다.

## 1. 기존 Phase 1 문서 확인

다음 문서를 실제 저장 경로에서 확인한다.

- BUSINESS_RULES.md
- DOMAIN_MODEL.md
- TEST_CASE_MATRIX.md
- DECISIONS.md
- 미결정 정책과 충돌 가능성 문서

기존 문서에 존재하는 Rule ID, OPEN ID, 충돌 ID를 유지한다.

Phase 1에서 잠정 결정한 정책은 사용자 승인 없이 확정된 것으로 처리하지 않는다.

## 2. 실험 범위 축소

이번 실험에서는 다음 기능만 구현한다.

1. 최근 12개 완료 월의 누적 사용금액 계산
2. 누적 금액에 따른 회원 등급 결정
3. 등급별 수수료율 결정
4. 수수료 계산 및 원 단위 반올림

등급 기준:
- BASIC: 1,000,000원 미만 / 3%
- SILVER: 1,000,000원 이상 / 2%
- GOLD: 5,000,000원 이상 / 1%
- VIP: 10,000,000원 이상 / 0.5%

기존 명세에 따라 당월 거래는 당월 등급 산정에 포함하지 않는다.

## 3. 이번 실험에서 제외

- 환불
- 거래 중복 방지
- DB 저장
- 정산 멱등성
- 동시성
- REST API
- 배치 처리
- 외부 시스템 연동

제외한 기능의 기존 명세는 삭제하지 않는다.

## 4. 잠정 정책

다음 정책을 실험용 가정으로 사용한다.

- OPEN-01: Asia/Seoul
- OPEN-03: 거래 금액 1~1,000,000,000원
- OPEN-04: HALF_UP, 월 합계에 1회
- OPEN-15: 고정 등급표 및 수수료율

시간 경계 테스트를 위해 Clock을 주입할 수 있도록 한다.

위 정책은 사용자 승인이 아니라 이번 실험의 임시 전제임을 명시한다.

기존 명세와 충돌하거나 구현에 추가 결정이 필요한 부분은 사용자에게 질문한다.

## 5. 구현

Java 21을 사용한다.

필요한 최소한의 도메인 클래스와 계산 메서드만 작성한다.

불필요한 계층, 인터페이스, 패턴을 추가하지 않는다.

테스트 코드, Jev 점수 산출, JaCoCo, PIT는 아직 수행하지 않는다.

AI가 최초 작성한 구현의 판단과 구조를 보존한다.

단, 컴파일에 필요한 최소 수정은 허용하고 기록한다.

## Turn 2 (AI 질문 → 사용자 응답, 2026-10-12)

AI 질문: 이번 범위에서 주입하는 Clock을 어디에 쓸까요? Phase 1 명세에서 정산월 M은 호출자가 지정하고, Clock은 'M이 이미 끝났는지(BR-STL-002)' 판단에만 쓰입니다. 그런데 BR-STL-002는 이번 포함 목록(누적 계산·등급·요율·수수료)에 명시되어 있지 않습니다.

선택지:
1. M 지정 + 마감 검증 (Recommended) — 호출자가 정산월 M을 넘기고, Clock으로 now < start(M+1)이면 거부(BR-STL-002 포함).
2. Clock이 대상 월 결정
3. M 지정, 마감 검증 없음

사용자 응답: "M 지정 + 마감 검증 (Recommended)"
