# 미결정 정책과 충돌 가능성

- 작성일: 2026-10-12 · Phase 1
- [BUSINESS_RULES.md](BUSINESS_RULES.md)에서 **[결정]** 으로 표시한 규칙은 요구사항에 없던 부분을 Phase 1에서 잠정 확정한 것이다. 명세를 모호하게 두지 않기 위해 값을 정했지만, **사용자 승인 전까지는 확정이 아니다.**

## 2. 규칙 간 충돌 가능성

| ID | 충돌 | 내용 | 현재 해소 방법 | 남는 위험 |
|----|------|------|----------------|-----------|
| C-01 | 요구-5 ↔ 요구-1 | 환불은 과거 귀속월을 감소시키는데, 그 월이 포함된 등급은 이미 확정됨. "그 달의 순사용금액"이 언제 보느냐에 따라 달라짐 | 순사용금액을 기준 시각(asOf)의 함수 `NU(m, asOf)`로 정의 (BR-PRF-001, BR-RFD-008) | 사용자·운영자가 "같은 달 실적이 정산마다 다르다"고 오해할 수 있음. 정산 결과에 `GB`와 산정 기간을 기록해 설명 가능하게 함 |
| C-02 | 요구-9 ↔ 요구-12 | 정산 후 환불된 금액에도 수수료가 부과된 채로 남음 | OPEN-05에서 의도된 정책으로 명시 | 고객 관점에서 과다 청구. 실제 서비스라면 조정 정산이 필요할 가능성 높음 |
| C-03 | 요구-7 ↔ 정상 반복 결제 | 같은 금액·같은 시각의 정상 결제 2건을 중복으로 오인할 위험 | 중복은 ID로만 판단 (BR-TXN-005) | 요청자가 ID를 잘못 재사용하면 정상 결제가 거부됨 (DUP-02) |
| C-04 | 요구-11 ↔ 데이터 최신성 | 멱등 재요청은 최신 데이터가 아니라 최초 확정 결과를 반환 | BR-STL-003에 의해 원래 결과가 변하지 않으므로 실제 차이 없음 | OPEN-02가 바뀌면(지연 거래 허용) 이 보장이 깨짐 → 재정산 정책 재검토 필요 |
| C-05 | 요구-2 "완료 월" ↔ 현실의 지연 데이터 | 실제로는 월이 끝난 뒤 늦게 도착하는 거래가 있음 | BR-TIM-003으로 소급 등록 금지 | 현실성 부족. Lab 범위에서 수용 |
| C-06 | 요구-8 ↔ BR-AMT-002 | 금액 상한과 long 사용으로 정상 경로에서는 오버플로가 일어날 수 없음 → `AMOUNT_OVERFLOW` 분기는 도달 불가능한 방어 코드가 됨 | 규칙은 유지 (안전장치) | 커버리지·Mutation 측정 시 이 분기가 미커버/생존 Mutant로 남을 수 있음. **실험 관찰 대상**으로 기록 |
| C-07 | BR-PRF-005 ↔ 운영 연속성 | 데이터 오류 하나로 해당 회원의 정산이 중단됨 | 오류를 숨기지 않는 쪽을 선택 | 운영 정책이 필요할 수 있으나 Lab 범위 밖 |
| C-08 | BR-TIM-003 ↔ 테스트 데이터 준비 | 과거 월 거래를 만들려면 Clock을 그 시점으로 바꿔 가며 등록해야 함 | Clock 주입 (BR-TIM-004), Fake 저장소 | Clock이 주입되지 않은 구현은 기간 경계 테스트가 사실상 불가능. **테스터빌리티 실험의 핵심 관찰 대상** |
| C-09 | BR-RFD-004 ↔ 동시성 | 잔여액 검사와 저장 사이에 경쟁이 생기면 초과 환불 발생 | 결제 단위 잠금 (DOMAIN_MODEL §3.3) | 메모리 Fake로는 DB 잠금 동작을 재현할 수 없음 → CON 테스트는 실제 DB(Testcontainers) 필요 |
