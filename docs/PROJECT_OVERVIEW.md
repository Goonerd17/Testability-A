# 프로젝트 개요 — AI Testability Lab

## 1. 목적

AI가 생성한 비즈니스 코드의 **테스터빌리티(Testability)** 를 실험하고, 그 과정과 결과를 AI 라이트닝 토크 세미나에서 발표한다.

- 이 프로젝트는 테스트 자동화 라이브러리/프레임워크를 만드는 것이 **아니다**.
- 관심사는 "AI가 처음 만든 코드가 얼마나 테스트하기 쉬운가, 어디서 테스트가 어려워지는가, 어떤 개입으로 개선되는가"이다.
- 모든 수치(커버리지, 복잡도, Mutation Score, 성능)는 실제 도구로 측정한 값만 사용한다.

## 2. 실험 대상 도메인

회원의 **최근 12개월 누적 사용금액**을 기준으로 **등급**을 산출하고, **등급별 차등 수수료**를 적용하는 **월별 정산 API**.

### 2.1 확정된 사항

- 등급 산출 기준: 최근 12개월 누적 사용금액
- 수수료: 등급별 차등 적용
- 정산 단위: 월별
- 제공 형태: REST API

| Q5 | 취소·환불 거래는 누적 사용금액에서 어떻게 처리하는가? | 원거래 월 차감 vs 취소 월 차감 |
| Q6 | 금액 단위·통화와 반올림/절사 규칙은? | 수수료 계산 시 소수점 처리, `BigDecimal` scale |
| Q7 | 가입 12개월 미만 신규 회원의 등급은? | 기본 등급 존재 여부 |
| Q8 | 정산 API의 입력/출력 형태는? | 회원 단위 조회인지, 월 전체 배치 실행인지 |
| Q9 | 같은 월을 재정산하는 경우의 동작은? | 멱등성 요구 여부 |
| Q10 | 시간대(Time Zone) 기준은? | 월 경계 판정에 영향 (예: Asia/Seoul) |

## 5. 작업 원칙 (요약)

1. 단계별로 진행하고 다음 Phase를 임의로 선행하지 않는다.
2. 불명확한 비즈니스 요구사항은 추측하지 않고 TODO/질문으로 남긴다.
3. 측정하지 않은 수치를 만들어내지 않는다.
4. AI 최초 생성 코드와 테스트는 비교를 위해 보존한다.
5. 테스트 실패를 이유로 업무 명세를 바꾸지 않는다.
6. 기능 코드와 테스트 코드를 동시에 수정해 테스트를 억지로 통과시키지 않는다.
7. 실행한 명령어, 결과, 실패 원인, 수정 이력을 기록한다.
8. 과거 회사의 비공개 소스나 고객 데이터를 사용하지 않는다.
9. 모든 설명과 문서는 한국어로 작성한다.
10. 테스트에서는 가능하면 Mockito보다 Fake 구현을 우선한다.
